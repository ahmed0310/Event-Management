1. STORED PROCEDURES (4 created - Minimum 3 required)
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   
   procAddEvent
   • IN Parameters: event_name, event_date, event_time, event_type, budget, venue_id, organizer_id
   • OUT Parameter: event_id (auto-generated and returned)
   • Features: Auto-generates unique event ID, inserts event record, commits transaction
   • Exception Handling: DUP_VAL_ON_INDEX, OTHERS
   • Use Case: Creating new events through application or API
   
   procRegisterParticipant
   • IN Parameters: full_name, gender, email, phone, address
   • Features: Validates gender (M/F), checks email uniqueness
   • Named Exceptions: v_invalid_gender, v_duplicate_email
   • Error Handling: Rolls back on validation failure, specific error messages
   • Use Case: Registering event participants with validation
   
   procProcessPayment
   • IN Parameters: participant_id, amount, payment_method, ticket_id
   • OUT Parameter: status (Success/Failed)
   • Features: Validates payment method, calls nested procedure, ensures consistency
   • Nested Call: Calls procUpdateTicketBooking
   • Exception Handling: NO_DATA_FOUND, custom validation
   • Use Case: Processing ticket payments with automatic record updates
   
   procUpdateTicketBooking (Nested)
   • IN Parameters: ticket_id, participant_id
   • Features: Updates ticket association, called by procProcessPayment
   • Use Case: Linking participants to tickets after payment

3. TRIGGERS (3 created - All types covered)
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   
   trgBeforeEventInsert (BEFORE INSERT)
   • Timing: Before event insertion
   • Logic: Auto-generates event_id, sets default budget (100,000)
   • Tables: Event
   • Meaningful Logic: Yes - Prevents NULL primary keys
   • Use Case: Automatic ID generation and default value assignment
   
   trgAfterPaymentUpdate (AFTER UPDATE)
   • Timing: After payment status change
   • Logic: Creates audit log entry with old/new values
   • Tables: Payment → AuditLog
   • Meaningful Logic: Yes - Complete audit trail
   • Use Case: Track payment status changes for compliance and debugging
   
   trgAfterTicketDelete (AFTER DELETE)
   • Timing: After ticket deletion
   • Logic: Archives deleted ticket to DeletedTickets table
   • Tables: Ticket → DeletedTickets
   • Meaningful Logic: Yes - Data preservation instead of loss
   • Use Case: Maintain historical records of canceled tickets

BUSINESS LOGIC HIGHLIGHTS
================================================================================

What Makes Phase 4 Implementation Meaningful:

1. AUTO-GENERATION
   • Event IDs are automatically generated (no manual entry)
   • Ticket IDs are auto-incremented
   • Prevents NULL primary keys with BEFORE INSERT trigger

2. DATA VALIDATION
   • Gender must be M or F
   • Email must be unique per participant
   • Payment method must be from approved list
   • Budget validation with CHECK constraints

3. AUDIT TRAIL
   • Every payment update is logged to AuditLog
   • Records old values, new values, user, and timestamp
   • Useful for compliance and debugging

4. DATA PRESERVATION
   • Deleted tickets are archived instead of permanently lost
   • Historical record available for analysis
   • DeletedTickets table maintains referential integrity

5. BUSINESS CALCULATIONS
   • Revenue calculation: Sum all ticket prices for event
   • Profit calculation: Revenue - Budget
   • Occupancy analysis: Count booked events per venue
   • Participant metrics: Count tickets per participant

6. TRANSACTION SAFETY
   • Nested procedure ensures consistent state
   • ROLLBACK on validation failure
   • COMMIT after successful operations

7. ENCAPSULATION
   • Package contains related procedures and functions
   • Package-level variables track state
   • Constants define business rules
